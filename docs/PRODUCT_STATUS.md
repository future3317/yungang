# 石窟光谱：当前产品状态与机制升级输入

本文档面向产品讨论、机制设计和网页版 GPT 评审。它只记录当前仓库已经存在或已经接入运行时的内容，不把计划数量写成已完成数量。

## 一、产品定位

玩家不是在管理后台，而是在一间数字遗产研究室中，通过移动、观察、交换和修护，让分散的文化证据重新形成可复查的关系。地图是世界，左右面板是 HUD；行动的价值来自证据组合、路线治理和事件取舍，而不是单纯抵达一个点。

## 三、玩家可执行行动

后端在 `GameState.action_options` 中返回当前行动选项。前端不得从动作类型或数组第一项推断目标。

每个 `ActionOption` 包含：

- `id`：选项稳定 ID；策略牌按具体卡牌分组。
- `type`：行动类型。
- `label`、`description`：玩家看到的行动语言。
- `cost.ap`：行动点成本。
- `enabled`、`disabled_reason`：可执行性与解释。
- `targets[]`：合法目标，每个目标带自己的 `payload` 和 `preview_delta`。
- `confirmation`：确认前提示。
- `payload`：不需要目标时的完整行动负载。

完整闭环是：

1. 选择行动。
2. 选择一个后端提供的合法目标，或直接确认无目标行动。
3. 显示成本、资源变化和风险预览。
4. 提交时按钮和弹窗锁定，并携带 `request_id` 与 `expected_revision`。
5. 成功后用前后状态差异显示 AP、线索、修护资源、威胁和影响变化。
6. 失败时解析 `detail.message`；revision 冲突则拉取最新状态并清空旧选择。

当前已覆盖移动、探索、贡献、修护、路线勘察、路线修护、建立连接、交换、技能、文化牌、策略牌、计划标记、事件回应、市场选择、弃牌和角色升级选择。

## 四、任务与项目判定

任务进度由后端写入 `task.progress`，包括：

- 证据数量。
- 研究领域覆盖。
- 来源多样性。
- 不同贡献者数量。
- 组合标签。
- 指定来源。
- `required_cards_per_player_min` 实际参与者最低贡献数。

项目阶段证据按 `stage_id` 隔离，并记录卡牌、贡献者和行动类型。阶段要求可以包含领域、来源多样性、贡献者、研究线索和修护资源。项目奖励完成后才进入终局目标统计。

## 五、事件与终局

事件在预告阶段根据场景、规则、种子确定 `event_targets`，结算阶段重复使用同一目标，不再按字典顺序临时选前两个对象。`event_instance.resolution` 记录实际目标、变化和原因。

终局结果包含：

- `outcome` 和内部 `outcome_reason`。
- 场景定义的 `outcome_summary`。
- 完成的目标和项目。
- 路线、任务、来源、守护、发现、资源和效率评分。

## 六、机制注册表

机制注册表位于 `backend/mechanisms.py`：

- `TRIGGER_HANDLERS`：节点能力触发器。
- `CULTURE_EFFECT_HANDLERS`：文化证据即时效果。
- `NODE_EFFECT_HANDLERS`：节点能力效果。
- `EVENT_EFFECT_HANDLERS`：事件结算效果。
- `ACTION_CARD_EFFECT_HANDLERS`：策略牌效果类型。
- `validate_content_mechanisms`：启动时扫描数据，发现未知效果、触发器或项目行动类型立即失败。

新增数据时，必须先注册运行时处理器，再提交 JSON。不要在 `engine.py` 中继续堆叠无法校验的大型 `if/elif`。

## 七、多人与单人

大厅使用席位令牌，不信任请求体中的玩家 ID 作为权限来源。多人客户端通过 `/api/rooms/{room_id}/events` 接收 revision 推送，再读取完整状态。SSE 断开后仍由 React Query 轮询兜底。

单人场景配置两位角色，由同一席位轮流控制；界面应明确说明这是一个玩家控制两个角色，而不是伪造另一名在线玩家。

## 八、当前待继续产品化事项

- 新增节点的专属插画仍可进一步替换；当前先复用已存在的主题素材，确保不出现破图。
- 运行时地图仍需要多控制点道路编辑器、路线检查器和布局导出工具。
- CSS 覆盖链、容器查询、独立组件预览和完整移动端三页结构仍需继续收敛。
- Playwright 全局流程、axe、Lighthouse、五种分辨率视觉回归和固定种子 100 次模拟需要实际执行并记录报告。
- 角色技能、升级和部分节点能力还需要逐项做行为测试，不能只依靠启动校验。

## 九、给机制评审模型的建议问题

1. 当前核心循环是否真的要求玩家在“移动、证据组合、路线治理、事件预案”之间做取舍？
2. 哪些节点、任务和策略牌只是换文案，没有形成不同决策？
3. 单人控制两个角色与多人协作的决策密度是否合理？
4. 来源多样性、项目阶段隔离和路线风险是否足以支撑重玩？
5. 下一轮内容扩展应优先增加新行动、替代路线，还是增加事件分支？请给出对玩家行为的可验证假设。
