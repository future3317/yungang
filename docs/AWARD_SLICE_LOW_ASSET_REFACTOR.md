# 《石窟光谱》低美术成本的参赛机制与重构路线

## 约束

- 不依赖持续手绘；新增位图只允许少量、可重复使用的背景或纹理。
- 现有地图、节点徽章、角色徽章、文化牌、事件图、场景图和交互框体继续使用。
- 先保证现有游戏始终可运行，再以独立模块接入新机制。
- 规则、内容、地图坐标和 HUD 几何分别配置；禁止把坐标散落在 React 组件中。

## 核心方向：证据互证，不做自由拼图

不制作需要大量专属碎片图的“壁画拼图”。把现有文化牌改造成可复用的证据单元，在一个由 CSS、SVG 和文字生成的“研究台”中建立关系：

1. 在当前节点选择一个既有 `site_facet` 观察。
2. 从当前节点的证据池揭示既有文化牌，而不是从全局市场无差别取牌。
3. 将证据放入“支持、冲突、待确认”三个关系槽。
4. 达到阶段条件后，在“立即处理、最小干预、先记录”之间选择。
5. 选择改变项目阶段、风险、事件链和结局档案。

文化内容通过卡名、摘要、来源、领域和既有图标表达；关系线、置信度、缺口和风险全部由 SVG/CSS 生成，不产生新的逐卡美术工作。

## 资产复用

| 现有资产 | 新用途 | 是否需要新图 |
| --- | --- | --- |
| 节点徽章 | 地图节点、研究台地点标识 | 否 |
| 文化牌图标 | 证据单元、关系节点 | 否 |
| 场景图 | 研究台背景、结局底图 | 否 |
| 事件图 | 环境压力和反转证据 | 否 |
| 角色徽章 | 不同观察权限和建议来源 | 否 |
| 路线与地图 | 宏观调度和跨地点互证 | 否 |
| 交互边框、表面、光环 | 置信度、选中、风险状态 | 否 |

如果确实需要生图，首个参赛切片只补三类通用图：一张研究台底纹、一张洞窟环境层、一张结局全景。它们不与单张卡牌绑定，可跨场景复用。

## 首个垂直切片

- 只启用一个核心场景和 6–8 个现有节点。
- 只选 12–15 张现有文化牌进入证据池。
- 只实现 3 种证据关系：支持、冲突、待确认。
- 只实现 3 种干预方案：立即处理、最小干预、先记录。
- 只制作一条三阶段事件链和三个结局档案。
- 保留现有移动、角色、事件与服务端合法行动协议。

目标是让玩家在前五分钟经历一次“新证据推翻原判断”，而不是展示更多菜单。

## 代码边界

### 保留

- `backend/engine.py` 继续是合法行动和结算的唯一来源。
- `ActionOption`、`pending_choice`、revision、固定 seed 和房间权限继续使用。
- `data/` 仍然是内容入口。
- `HeritageNetwork` 继续负责宏观地图，不承担证据规则。

### 新增模块

建议按以下边界逐步加入，不直接扩大 `GamePage.tsx`：

```text
backend/
  domain/
    interpretation.py       # 证据关系、置信度、冲突和阶段完成判定
  selectors/
    interpretation.py       # 生成相关 ActionOption

frontend/src/features/interpretation/
  InterpretationBoard.tsx   # 纯展示与目标选择
  EvidenceNode.tsx
  InterventionChoice.tsx
  interpretationView.ts     # 将服务端状态投影为 UI 数据
```

建议状态：

```json
{
  "interpretation": {
    "site_id": "yungang",
    "question_id": "q_material_trace",
    "placements": [
      { "card_id": "culture_07", "relation": "support", "player_id": "p1" }
    ],
    "confidence": 2,
    "conflicts": [],
    "intervention": null
  }
}
```

第一版不做自由坐标拖放。证据只进入固定关系槽，既减少交互错误，也不需要为手机端再设计一套玩法。

## UI 与定位调试规则

- 地图节点坐标继续由 `data/sites.json -> layout` 和 `/dev/map-editor` 管理。
- 路线路径继续由 `data/routes.json -> waypoints` 管理。
- HUD 几何只通过以下 CSS 变量管理：
  - `--hud-left-width`
  - `--hud-right-width`
  - `--hud-center-gutter`
  - `--hud-panel-top`
  - `--hud-panel-bottom`
  - `--hud-footer-bottom`
- 开发环境的游戏页右下角提供“布局”工具，也可按 `Ctrl+Shift+L` 打开。
- 调整结果保存在本机；“复制 CSS”可生成能直接回填 `tokens.css` 的变量。
- 不再允许为单个分辨率复制一组 `top/left/right` 数字；紧凑高度只覆盖基础变量。

## 实施顺序

1. 集中 HUD 布局变量和开发调试工具，不改变规则。
2. 从 `GamePage` 抽出 `GameShell`、动作编排 hook 和对话框层。
3. 新增只读的 `InterpretationBoard`，用现有牌验证视觉和交互。
4. 后端接入放置证据、修正关系和选择干预三个动作。
5. 用一个场景完成 20–30 分钟纵向切片。
6. 试玩确认有推理和反转后，再扩展其他场景，暂不增加大量新卡和新节点。

## 工作量控制

首个可试玩版本应控制在：

- 后端新动作 3–4 个；
- 前端新核心组件 3 个；
- 新位图 0–3 张；
- 新文化文本只覆盖一个场景；
- 不重做地图、不重做卡牌框、不重做角色系统；
- 不同时改多人同步协议。

这条路线的重点是把既有内容重新组织成一个可记忆的核心抉择，而不是重新制作一套游戏。
